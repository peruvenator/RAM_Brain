# HubSpot Integration — Return Stacked Advanced Visualizer Widget

How the widget submits contact and event data to HubSpot. All widget code lives in a single file: `RS_advanced_visualizer_widget.html` (generated by `py -3.11 build_widget.py`).

---

## Current State (as of 2026-06-25)

- The **intake gate has been removed**. The widget loads immediately without asking for name, email, or investor type.
- The **consultant CTA is ungated** — it renders for all users (previously gated on investor type).
- Email identity is now expected to come from WordPress via a `window.RSV_CONFIG` injection (see below). Until that is wired up, HubSpot submissions will fire with an empty email field.
- All HubSpot submissions use the public **Forms API v3** (`https://api.hsforms.com/submissions/v3/integration/submit/...`) — no API key required, fire-and-forget, failures are swallowed silently.

## WordPress Identity Injection (pending developer implementation)

The widget reads a page-level config object before anything else runs:

```js
// In RS_advanced_visualizer_widget.html, lines ~9178-9194
(function() {
  if (window.RSV_CONFIG && RSV_CONFIG.userEmail) {
    storedEmail     = RSV_CONFIG.userEmail;
    storedFirstName = RSV_CONFIG.firstName || '';
    storedLastName  = RSV_CONFIG.lastName  || '';
    return;
  }
  // falls back to localStorage if RSV_CONFIG not present
})();
```

**What the WordPress developer needs to do:** On the page that embeds the widget, inject the following `<script>` block *before* the widget HTML loads, using the logged-in WordPress user's data:

```html
<script>
window.RSV_CONFIG = {
  userEmail: '<?php echo esc_js( wp_get_current_user()->user_email ); ?>'
};
</script>
```

When this is in place:
- `storedEmail` is populated from the WP user automatically
- Share link and PDF download HubSpot submissions carry the correct email
- The user info strip in the widget header shows name + email if both are present
- The localStorage fallback is still in place for any non-WP context

## The Shared Submit Helper

```js
function submitHubSpotForm(formId, fields) {
  fetch('https://api.hsforms.com/submissions/v3/integration/submit/' + HS_PORTAL_ID + '/' + formId, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ fields: fields })
  }).catch(function() {});
}
```

- Public, unauthenticated endpoint — no API key needed
- Each `fields[]` entry: `{ objectTypeId: '0-1', name, value }` — `objectTypeId: '0-1'` is HubSpot's Contact object
- No `hutk` cookie, no session context block — submissions are raw contact property updates, not tied to a HubSpot visitor session
- No retry, no error reporting

## Active HubSpot Events

### 1. Share Link

**Trigger:** User clicks the "Share Link" button on any portfolio tab.

**Fields:**
```js
submitHubSpotForm(HS_SHARE_FORM_ID, [
  { name: 'email',                  value: storedEmail },
  { name: 'portfolio_widget_output', value: 'Core: ... \nStack: ...' }
]);
```

### 2. PDF Download

**Trigger:** User clicks "Export PDF" on any portfolio tab, or "Download Comparison PDF" in a comparison panel.

**Fields:**
```js
submitHubSpotForm(HS_PDF_FORM_ID, [
  { name: 'email',                  value: storedEmail },
  { name: 'portfolio_widget_output', value: 'Core: ... \nStack: ...' }
]);
```

### 3. Consultant Modal (AUM + State)

**Trigger:** User opens "Talk to a Consultant" CTA, selects AUM range and state, clicks "Find My Consultant."

**Fields:**
```js
submitHubSpotForm(HS_CONSULTANT_FORM_ID, [
  { objectTypeId: '0-1', name: 'email',                   value: storedEmail },
  { objectTypeId: '0-1', name: 'investable_assets',       value: aumToHubSpotValue[selectedAum] },
  { objectTypeId: '0-1', name: 'state_province_dropdown', value: selectedState }
]);
```

AUM widget labels do not match HubSpot picklist values — a translation table (`aumToHubSpotValue`) maps between them. If either side renames an option, submissions will silently fail on that field.

AUM + state are cached in `localStorage` (`INTAKE_STORAGE_KEY`) so returning users skip step 1 of the modal.

### 4. Consultant Booking (URL params, no form)

**Trigger:** User clicks "Schedule with [Name]" in the consultant modal.

Opens the consultant's HubSpot Meetings URL in a new tab with identity + portfolio pre-filled as query params:

```js
const params = new URLSearchParams({
  firstName:               storedFirstName,
  lastName:                storedLastName,
  email:                   storedEmail,
  portfolio_widget_output: '...'
});
window.open(consultantUrl + '?' + params.toString(), '_blank');
```

Consultant routing is state-based (`stateToConsultant` map) with one AUM override: Dillon Pierce's states + AUM under $100M routes to Richard Laterman instead.

## localStorage Schema

Key: `rsWidgetIntake`

```json
{
  "firstName":    "...",
  "lastName":     "...",
  "email":        "...",
  "investorType": "...",
  "aum":          "...",
  "state":        "..."
}
```

- `firstName / lastName / email / investorType` — previously set by the intake gate; now only written if a user completes the consultant modal flow or if a legacy localStorage entry exists from a prior session
- `aum / state` — written when user completes consultant modal step 1; used to skip step 1 on return visits
- When `RSV_CONFIG.userEmail` is present on page load, it takes priority and the localStorage email fields are ignored

## What Is Not Wired Up

- No HubSpot tracking pixel (`hs-scripts.com`) — no page-view or session tracking
- No `hutk` cookie capture — submissions are not associated with a HubSpot visitor session
- No `context` block on submissions (no `pageUri`, `pageName`, `ipAddress`)
- No GDPR consent payload
- No retry or error telemetry on failed submissions
- No GA / GTM / dataLayer integration
- No behavioral event tracking (allocation changes, tab switches, etc.)
